# How Real Software Organizations Staff and Run the "Build" Phase

Research date: 2026-07-25

## Roles

- **Software Engineer (IC levels)**: Companies almost universally publish multi-level IC ladders alongside a parallel management track so engineers can grow without switching to people management. Dropbox's public Engineering Career Framework defines "Level Expectations" (scope, collaborative reach, levers for impact) plus "Core and Craft Responsibilities" scored across Results, Direction, Talent, and Culture pillars, covering software engineers, QA engineers, ML engineers, and engineering managers as separate tracks. [Dropbox: Sharing our Engineering Career Framework](https://dropbox.tech/culture/sharing-our-engineering-career-framework-with-the-world), [Dropbox Career Framework site](https://dropbox.github.io/dbx-career-framework/). Square/Block's ladder starts ICs at L3 and managers at L5, with each level's criteria cumulative on the prior level's. [Square Growth Framework](https://developer.squareup.com/blog/squares-updated-growth-framework-for-engineers-and-engineering-managers/), [Square ladder PDF via progression.fyi](https://progression.fyi/f/square). CircleCI runs a six-level E1–E6 ladder (Associate Engineer → Principal Engineer), with E1–E3 scoped to task/epic/team and higher levels scoped to org/company; explicitly one ladder for all engineers, no forced management switch. [CircleCI: 7 steps to building a competency matrix](https://circleci.com/blog/7-steps-to-building-an-engineering-competency-matrix/), [CircleCI: why we re-designed our paths](https://circleci.com/blog/why-we-re-designed-our-engineering-career-paths-at-circleci).

- **Tech Lead / Staff / Principal Engineer**: Rent the Runway's 2015 ladder — one of the first public ones — splits post-senior progression into a "Manager" track and an "Architect" track, framing the classic build-vs-lead-people fork explicitly. [Every Public Engineering Career Ladder (swyx)](https://swyx.io/career-ladders), [10 Years of Engineering Ladders (Camille Fournier)](https://skamille.medium.com/10-years-of-engineering-ladders-329d309000cd). Staff/Principal engineer is the senior IC role focused on scope beyond a single team (org- or company-wide technical direction), as reflected in CircleCI's E4–E6 (Staff, Senior Staff, Principal) definitions above.

- **Engineering Manager / Tech Lead Manager**: Dropbox and Square both define EM as a distinct ladder rather than a senior-IC extension; "Tech Lead Manager" (hybrid IC+people-management) appears informally across these frameworks though it is not always a named level — treat the TLM label itself as `[unsourced]` for these specific companies even though the EM and IC-lead concepts are sourced above.

- **Software Architect vs Solutions Architect vs Platform Engineer**: The community draws a recurring distinction between "architect" as a design-authority role (system integrity, cross-team risk mitigation) versus a coding IC role. See the "should architects code" debate in Practice Variation below for primary sources on how the architect role is defined and contested. Solutions Architect and Platform Engineer as distinct titles were not found with primary-source role definitions in this pass; mark specific responsibility splits for these two titles as `[unsourced]`.

- **progression.fyi as an aggregator**: An open collection of public "progression frameworks" (career ladders / competency matrices) voluntarily published by companies including Etsy, GitLab, Brandwatch, Meetup, Square, CircleCI, and Dropbox, maintained by the founders of Progression. [progression.fyi about page](https://progression.fyi/about/), [progression.fyi Dropbox entry](https://progression.fyi/f/dropbox), [progression.fyi Square entry](https://progression.fyi/f/square), [progression.fyi CircleCI entry](https://progression.fyi/f/circle-ci). A parallel community-maintained aggregation exists on GitHub. [bmoeskau/engineering-ladders](https://github.com/bmoeskau/engineering-ladders).

## Responsibility boundaries

- At Rent the Runway's "Engineer 2" level, an IC is expected to own small-to-medium features end-to-end "from technical design to launch," self-prioritize, and unblock themselves — illustrating where IC technical-design responsibility starts before any lead/architect role is required. [10 Years of Engineering Ladders](https://skamille.medium.com/10-years-of-engineering-ladders-329d309000cd).
- Square's ladder makes level criteria strictly additive (an L4 must still meet all L3 criteria), which is a common design pattern meant to make the boundary between adjacent levels legible rather than a step-change in role. [Square Growth Framework blog](https://developer.squareup.com/blog/squares-updated-growth-framework-for-engineers-and-engineering-managers/).
- The architect-vs-IC boundary is explicitly contested rather than settled — see Practice Variation.
- Google's readability program draws a boundary within code review itself: any reviewer can approve a change for correctness, but at least one participant must additionally hold a per-language "readability" certification before certain changes can land, separating "is this correct" from "is this idiomatic/maintainable" as distinct review responsibilities. [Google eng-practices: Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html), [Software Engineering at Google, ch. 9 (Code Review)](https://abseil.io/resources/swe-book/html/ch09.html), [How Google does code review — Graphite](https://graphite.com/blog/how-google-does-code-review).

## Artifacts produced

- **RFC (Request for Comments)**: At Uber, an RFC is a high-level proposal an engineer circulates (originally via mailing list, later formalized) describing a new service's purpose, architecture, and dependencies, with an explicit "approver" field so key stakeholders can sign off or object; templates standardize required content like SLAs and third-party dependencies. Authored by the engineer(s) proposing the change; reviewed/approved by named approvers and the wider team via comment threads. [Pragmatic Engineer: Scaling Engineering Teams via RFCs](https://blog.pragmaticengineer.com/scaling-engineering-teams-via-writing-things-down-rfcs/), [Increment: Planning for change with RFCs](https://increment.com/planning/planning-with-requests-for-comments/).
- **RFD (Request for Discussion)**, Oxide Computer's variant: an AsciiDoc document living in a git repo, discussed via an associated GitHub pull request, moving through states Prediscussion → Ideation → Discussion → Published → Committed (or Abandoned). Explicitly modeled on the Golang proposal process, Joyent's RFD process, the Rust RFC process, and the Kubernetes proposal process. Authored by any engineer; discussed/reviewed by the team inline via PR comments; "published" once discussion converges. [Oxide: RFD 1 Requests for Discussion](https://oxide.computer/blog/rfd-1-requests-for-discussion), [Oxide: A Tool for Discussion](https://oxide.computer/blog/a-tool-for-discussion), [oxidecomputer/rfd-site on GitHub](https://github.com/oxidecomputer/rfd-site).
- **Rust RFC**: A formal proposal document required for "substantial" changes (language/library semantics, feature removal, or changes to the RFC process itself) — ordinary bug fixes go through normal PRs instead. Authored by any contributor via a PR against rust-lang/rfcs; the PR itself is the review venue; the Rust core team merges (accepts, making it "active") or closes (rejects) it. Acceptance is not a guarantee of eventual shipping. [rust-lang/rfcs: 0002-rfc-process.md](https://github.com/rust-lang/rfcs/blob/master/text/0002-rfc-process.md), [The Rust RFC Book](https://rust-lang.github.io/rfcs/0002-rfc-process.html).
- **Design doc (Google-style)**: An informal-format document written before coding begins, covering high-level implementation strategy and, centrally, the trade-offs considered among design alternatives. Authored by the engineer(s) leading the work; reviewed via inline comment threads and, for higher-stakes designs, a live design-review meeting where the author presents to senior engineers. [Design Docs at Google (industrialempathy.com)](https://www.industrialempathy.com/posts/design-docs-at-google/), [Pragmatic Engineer: Google's Engineering Culture](https://newsletter.pragmaticengineer.com/p/googles-engineering-culture).
- **ADR (Architecture Decision Record)**: A short text file recording one architectural decision, in Michael Nygard's original format: Title, Status, Context, Decision, Consequences. Nygard's stated goal was to make the motivation behind past decisions visible to future engineers, using a lightweight format compatible with agile delivery. Authored by whoever makes/proposes the decision; in governed organizations, reviewed/approved by an architect or Architecture Review Board (see Gates). [Nygard, "Documenting Architecture Decisions," 2011 (Cognitect)](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions), [adr.github.io](https://adr.github.io/), [adr.github.io templates page](https://adr.github.io/adr-templates/). ThoughtWorks placed ADRs in the "Adopt" ring of its Technology Radar, evidencing industry uptake beyond the originating author, per the same aggregator source above.
- **C4 model diagrams**: A four-level (Context, Container, Component, Code) notation-independent diagramming approach for visualizing software architecture at different zoom levels for different audiences, created by Simon Brown. Explicitly positioned as an aid to architecture reviews, onboarding, risk-storming, and threat modeling — not just documentation for its own sake. Authored typically by whoever owns the system/component being diagrammed; consumed by architects, reviewers, and new team members. [c4model.com Introduction](https://c4model.com/introduction), [c4model.com Diagrams](https://c4model.com/diagrams), [c4model.com Home](https://c4model.com/).
- **API contract / OpenAPI spec, data model & migration plan, spike report, estimation artifacts (story points/t-shirt sizing), task breakdown**: These are standard build-phase artifacts referenced throughout agile/engineering practice literature, but a primary-source definition of "who authors/reviews" each specifically was not captured with a verifiable URL in this pass beyond the spike definition below; treat unlinked claims about these as `[unsourced]`.
- **Spike (agile/XP)**: A time-boxed investigation (not a deliverable) whose output is knowledge — reducing risk on a technical approach, clarifying a requirement, or firming up a story estimate — rather than shippable code. Originates from Extreme Programming; SAFe also formalizes "Spikes" as a work item type. Authored/run by the engineer(s) assigned the investigation; the output ("spike report") informs the team's subsequent estimation and design decisions. [Scaled Agile Framework: Spikes](https://scaledagileframework.com/spikes/), [Mountain Goat Software: What Are Agile Spikes?](https://www.mountaingoatsoftware.com/blog/spikes), [Wikipedia: Spike (software development)](https://en.wikipedia.org/wiki/Spike_(software_development)).
- **Build-vs-buy analysis**: A structured comparison (strategic alignment/core-differentiation test, cost, time-to-market, risk, maintenance opportunity cost) used to decide whether to build a capability in-house or acquire it; commonly authored by the engineering lead or architect proposing the capability and reviewed by engineering/product leadership before commitment. [Forbes Tech Council: Build vs Buy Decision Framework](https://www.forbes.com/councils/forbestechcouncil/2024/10/07/a-comprehensive-guide-to-the-build-versus-buy-decision-framework/), [Windward Studios: Build vs Buy Framework](https://www.windwardstudios.com/blog/build-buy-framework-development).
- **Threat model / STRIDE analysis**: Produced during the design phase, before code is written, as part of architecture review; the "STRIDE per element" method walks the design diagram's entry points and trust boundaries (network, file, registry, etc.) to enumerate Spoofing/Tampering/Repudiation/Information-Disclosure/DoS/Elevation-of-Privilege threats. Microsoft's Security Development Lifecycle made STRIDE-based threat modeling a mandatory design-phase gate since 2004. Authored typically by the engineer/architect owning the design, often reviewed by a security team. [Microsoft Learn: Security Briefs — Threat Models Improve Your Security Process](https://learn.microsoft.com/en-us/archive/msdn-magazine/2008/november/security-briefs-threat-models-improve-your-security-process), [Microsoft Threat Modeling Tool overview](https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool), [Practical DevSecOps: STRIDE Threat Model](https://www.practical-devsecops.com/what-is-stride-threat-model/).

## Handoff points

- **Spec/design → implementation**: In the Google design-doc culture, once a design doc has passed comment-thread review (and, for larger designs, a live design-review meeting with senior engineers), the author proceeds to implementation with the design doc serving as the reference the eventual code is checked against. [Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/).
- **RFC/RFD acceptance → implementation**: In both Uber's RFC process and Oxide's RFD process, "acceptance"/"published" state is the handoff signal that lets engineers begin building against the proposal; the Rust RFC process is explicit that PR-merge ("active" status) is exactly this handoff point, and even then acceptance is not a guarantee the resulting implementation will ultimately ship. [rust-lang/rfcs process doc](https://github.com/rust-lang/rfcs/blob/master/text/0002-rfc-process.md), [Oxide: RFD 1](https://oxide.computer/blog/rfd-1-requests-for-discussion).
- **Implementation → code review**: At Google, essentially every change is reviewed before being committed; the flow is typically an LGTM from a peer engineer followed by approval from a code owner or a readability-certified reviewer for changes touching areas requiring that certification. [Google eng-practices: How to do a code review](https://google.github.io/eng-practices/review/reviewer/), [Software Engineering at Google, ch. 9](https://abseil.io/resources/swe-book/html/ch09.html).
- **Code review → merge**: GitHub branch protection operationalizes this handoff as a technical gate — a pull request cannot merge to a protected branch until it has the configured number of approving reviews and all required status checks (CI) pass; organizations can enforce this uniformly via org-wide rulesets. [GitHub Docs: About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [GitHub Docs: Managing a branch protection rule](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule).

## Gates and decision criteria

- **Architecture Review Board (ARB) / ADR approval**: In enterprise governance models, an architect drafts an ADR with status "Proposed"; the ARB reviews context/alternatives/rationale and may request changes; once approved, status becomes "Accepted" with a recorded decision date, and the accepted ADR governs subsequent decisions in its domain. Tiered authority is common: day-to-day decisions at Project Architect level, standard variances at Domain Architect level, high-risk/non-conforming choices requiring full ARB plus Executive Sponsor sign-off, and strategic platform choices requiring ARB plus Executive Committee approval. [LeanIX: Architecture Review Board](https://www.leanix.net/en/wiki/ea/architecture-review-board), [Conexiam: What Is an Enterprise Architecture Review Board?](https://conexiam.com/what-is-an-enterprise-architecture-review-board/), [Sparx Services: What Is an ADR?](https://sparxservices.com/insights/insight-104-what-is-adr/). GitLab publishes its own ARB charter as a real-world example. [GitLab Handbook: Architecture Review Board](https://handbook.gitlab.com/handbook/eta/arb).
- **Rust RFC gate**: The core team is the sole body empowered to merge (accept) or close (reject) an RFC PR; community discussion informs but does not itself decide. [rust-lang/rfcs process doc](https://github.com/rust-lang/rfcs/blob/master/text/0002-rfc-process.md).
- **Code review approval gate**: At Google, at least one reviewer must hold "readability" certification (obtained per programming language) for a change to be approvable in that language — a mandatory, named-role gate layered on top of ordinary peer LGTM. [Google eng-practices: Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html), [HackerOne: Getting the Certification to Review Code at Google](https://www.hackerone.com/blog/getting-certification-review-code-google).
- **Branch protection / CI gates**: Configurable hard gates — required number of approvals, required passing status checks, required conversation resolution, linear history / signed commits — block merge until satisfied; repository admins and, at the org level, org-wide rulesets, decide who can configure and who can bypass these gates. [GitHub Docs: About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
- **Definition of Done**: Per the Scrum Guide, a Product Backlog Item or Increment cannot be called "Done" until it meets a shared, team-defined criteria set; it is created collaboratively by the Product Owner, Developers, and Scrum Master during sprint planning as a quality gate before release. [Scrum.org: What is a Definition of Done?](https://www.scrum.org/resources/what-definition-done), [Atlassian: Definition of Done](https://www.atlassian.com/agile/project-management/definition-of-done).
- **Threat-modeling gate**: Microsoft's SDL made STRIDE-based threat modeling for new designs mandatory before code is written, framed as cheapest to fix at the design stage; Microsoft states this measurably reduced vulnerability counts in shipped products. [Microsoft Learn: Security Briefs](https://learn.microsoft.com/en-us/archive/msdn-magazine/2008/november/security-briefs-threat-models-improve-your-security-process).

## Practice variation and open debates

- **Should architects code?** This is an explicitly unresolved, long-running industry debate. One side (echoing Joel Spolsky's 2001 "Architecture Astronaut" critique) argues non-coding architects become detached from real system constraints and risk becoming "PowerPoint/ivory-tower architects" who use "archibabble" to impress non-technical stakeholders while offloading real problems to developers. The opposing/moderating view (associated with Martin Fowler) is that architects should stay close to code, e.g. via pair programming with developers, while their core responsibility remains system-wide integrity and risk rather than line-level implementation; within the agile community specifically, the position is often stated flatly as "good architects code, end of discussion." A middle pragmatic take is that architects should keep skills current without necessarily shipping customer-facing code themselves. [IEEE Software Blog: Why Should Software Architects Write Code?](http://blog.ieeesoftware.org/2016/02/why-should-software-architects-write.html), [InfoQ: Should Architects Code](https://www.infoq.com/news/Should-Architects-Code), [InfoQ: Architects Should Code (Bryson)](https://www.infoq.com/articles/architects-should-code-bryson), [Simon Brown: the software architecture role is about coding, coaching and collaboration](https://dev.to/simonbrown/the-software-architecture-role-is-about-coding-coaching-and-collaboration-4gp3), [Ben Morris: Why agile software architects should write code](https://www.ben-morris.com/why-agile-software-architects-should-write-code/).
- **RFC-heavy vs RFC-light**: Uber's own retrospective notes the RFC process only "stuck" because it started early while the org was still small, and had to be actively tuned over time (segmented mailing lists to cut noise, adding formal "approver" fields, adding templates) as the company scaled from tens to low thousands of engineers — implying RFC weight is not a fixed setting but something orgs actively recalibrate as they grow, and that a process introduced too late may not take root the same way. [Pragmatic Engineer: Scaling Engineering Teams via RFCs](https://blog.pragmaticengineer.com/scaling-engineering-teams-via-writing-things-down-rfcs/). Rust's RFC process explicitly reserves the heavyweight process for "substantial" changes only, routing everything else through ordinary PR review — an explicit RFC-light default with RFC-heavy carve-outs. [rust-lang/rfcs process doc](https://github.com/rust-lang/rfcs/blob/master/text/0002-rfc-process.md).
- **Trunk-based development vs GitFlow**: Current commentary (2025) frames GitFlow's long-lived branches as increasingly mismatched with CI/CD — merge conflicts compound the longer a branch lives, and GitFlow "optimizes for control, not speed." Trunk-based development (short-lived branches, feature flags) is presented as the better fit for fast-paced, CI/CD-centric teams, while GitFlow is argued to still suit structured, versioned releases. One cited empirical framing: trunk-based development favors smaller, more experienced teams, while branch-based development suits larger, less-experienced teams — a real (if informally sourced) trade-off rather than a one-sided verdict. [Mergify: Trunk-Based Development vs Gitflow](https://mergify.com/blog/trunk-based-development-vs-gitflow-which-branching-model-actually-works), [Toptal: Trunk-based Development vs. Git Flow](https://www.toptal.com/developers/software/trunk-based-development-git-flow), [arXiv: Choosing the Right Git Workflow](https://arxiv.org/html/2507.08943v1).
- **Mob/pair programming vs individual ownership**: `[unsourced]` in this research pass — no primary source was retrieved comparing these directly; the architects-should-code sources above touch pairing only as a collaboration mechanism between architects and developers, not as a general staffing debate.
- **How AI coding agents (2025–2026) are changing code review**: Commentary describes 2023 as the "AI code completion" year, 2024–2025 as the rise of AI-native IDEs, and 2026 as an "agent engineering" phase where engineers assign work to agents rather than asking for line-level help. A specifically named risk: AI agents are now involved in producing a majority of shipped code at some organizations, changes are more voluminous, but human review capacity/time has not scaled proportionally — creating a growing gap between code entering production and code actually read by a human. The claimed shift in required skill is away from writing code and toward judging when *not* to trust AI-generated code and knowing where agents systematically fail; architecture, decision-making, and cross-team judgment are argued to remain human-centered even as code authorship shifts to agents. [Anthropic: 2026 Agentic Coding Trends Report](https://resources.anthropic.com/2026-agentic-coding-trends-report), [Hitechies: The best engineers in 2026 aren't the best coders](https://www.hitechies.com/ai-coding-agents-developer-skills-code-review-2026/), [arXiv: Professional Software Developers Don't Vibe, They Control (2025)](https://arxiv.org/pdf/2512.14012).
